# v0.1.4: VS Code loading recovery and storage-test fixes

## Improvements and bug fixes

- **Recover from a blocked VS Code load.** If the embedded editor is still loading after eight seconds, Kintsugi offers **Open VS Code directly** and **Retry**. Safari can hide a certificate warning inside the iframe; opening the editor in a full tab lets you review the warning, then Retry reloads the editor in its original pane. Normal loading is unchanged, and certificate checks and workspace-origin isolation remain in place.
- **LAN verification follows the current live-update protocol.** The physical LAN client verifier now checks SSE subscriptions and HTTP commands instead of expecting a live-update WebSocket. Terminal and Desktop WebSockets are unchanged.
- **Tests support both storage backends.** Repository-builder scenarios now run for EROFS and OverlayFS, and OverlayFS preload tests cover AMD64 and ARM64. EROFS cache fixtures no longer inherit the host's storage setting, and updater fixtures declare support for both drivers. These changes fix tests that previously failed in OverlayFS development workspaces; they do not change production storage behaviour.
- **More reliable preview-origin tests.** The retained-origin test no longer assumes that a port next to a free port is also available, and always cleans up its listeners.

## Verification

- Lint and TypeScript checks passed.
- Full local suite: 2,065 passed, 39 skipped, no failures.
- The retained-origin test passed twenty consecutive runs.
- The VS Code recovery flow was checked in Chromium and WebKit with a deliberately stalled iframe, including opening the isolated editor endpoint and retrying in the original iframe. Safari's native certificate approval on macOS was not automated.

This patch uses the existing download-and-restart update flow. Publication does not restart an installation, and `stable` is unchanged.
