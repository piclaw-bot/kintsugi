# Kintsugi v0.3.4

## Workspace caps may overlap

Workspace RAM, additional swap and CPU settings are limits, not reservations. This patch fixes resource control treating the sum of configured RAM/swap maxima as preallocated capacity, which could reject a start or park a healthy workspace even when actual usage was low.

- Configuration and startup no longer subtract other workspaces' caps from the shared budget.
- Recovery no longer stops healthy workspaces merely because their caps overlap.
- Properties labels and automation guidance explain that displayed cap sums are informational.
- Each workspace still has finite, individually validated limits. The aggregate workload cgroup boundary, host/management headroom, PID limits, memory-reduction acknowledgement, pending-apply safeguards and OOM cooldown remain unchanged.

Overlapping caps do not guarantee that every workspace can reach its maximum simultaneously. Actual concurrent use remains constrained by the shared boundary.

## Workspace startup no longer waits for closed Changes

Opening a workspace used to capture its entire Changes snapshot even when that view was closed. Sequential repository operations could exceed the workspace presentation deadline and show “Workspace unavailable” despite healthy containers and gateways. Attachment now returns view metadata without capturing the repository; agent-turn completion also skips Changes that has never been opened. Explicit Changes requests still capture normally, with the existing file-read/content budgets intact.

This isolates large repository scans from normal workspace and agent startup. It does not make opening Changes on very large trees fast.

## Verification

PR [#8](https://github.com/rcarmo/kintsugi/pull/8) passed the full pull-request CI run before merge. Focused resource-control, server-rendering and compatibility checks passed 32 tests with 140 assertions, including concurrent overlap, configuration with running/pending peers, 4+2+2 GiB caps, shared swap and retained failure/OOM safeguards. Module generation, lint, TypeScript and the System bundle build passed locally.

On the affected Orange Pi 6 Plus (CIX P1 ARM64, 12 cores, approximately 14.85 GiB usable RAM, Debian Trixie/Linux 6.6.89-cix), the supervisor fix allowed all three existing workspaces to run with 4+2+2 GiB caps. Their HTTPS pages returned 200, while the shared 6,104,031,232-byte workload cap remained unchanged and no new OOM was observed during the startup verification. This was not a sustained active-agent stress test or reboot test.

The initial HTTP 200 checks above covered only page shells, not usable workspaces. The subsequent presentation failure was reproduced in Chromium and traced to Changes attachment: one capture exceeded 22 seconds after roughly 50 Docker batches; the firmware worktree contained 20,642 changed/untracked entries. PR [#9](https://github.com/rcarmo/kintsugi/pull/9) removes that eager dependency. Its local Changes suite passed **95 tests, 483 assertions**, including an unopened-attachment/turn-completion regression and explicit-capture failure propagation. Generation, lint and TypeScript passed.

After an app-only local patch/restart, all three workspaces rendered their saved conversations in Chromium; admin details completed in 30–83 ms. A disposable terminal created through the app delivered its expected output over browser WebSocket and was closed afterwards. Workspace containers and start times were unchanged. This verifies ordinary presentation and terminal access, not sustained agent stress or large-tree Changes performance.

The version tag runs the full release checks and native AMD64/ARM64 image verification. GitHub Release creation and `latest` promotion occur only after those gates succeed; a tag or this source note alone is not proof of completed publication.

## Compatibility and rollout

No stored policy format or capability change: System capability **3**, default app minimum **0**, network-policy reader **2**, resource-policy reader **1**. Updating the System component is necessary for the corrected admission/recovery behaviour; the app update supplies the Changes attachment fix. An app-only update is insufficient for both fixes. Existing workspace limits and data are retained.

Publication advances `latest` and leaves `stable` unchanged. It does not update or restart an installation. Local supervisor/app workarounds applied before publication can be superseded by the released pair through the supported updater.
